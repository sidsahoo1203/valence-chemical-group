# Run in your own Postman

1. Import `Valence.postman_collection.json` and `Valence.postman_environment.json` into your Postman account/local app. Select the imported environment.
2. Set `baseUrl=http://localhost:5000/api` and `frontendOrigin=http://localhost:5173` for local Express/Vite. For deployment, use your API's HTTPS `/api` URL and the exact frontend origin configured on Render.
3. Fill `buyerEmail`, `buyerPassword` with a new test buyer YOU choose. Fill `adminEmail`, `adminPassword` with YOUR seeded administrator. Keep these values private/local. Never commit or share an environment exported with populated secrets.
4. Run folders 01–06 in order, one request at a time initially. Assertions verify expected status codes and that guest RFQ/contact records reach staff queues. The scripts capture record IDs and separate buyer/admin access tokens. Registration is not rerun-safe: use a new buyer or skip the initial registration request on later runs.
5. Postman's cookie jar stores the HttpOnly refresh cookie automatically. Leave the `refreshToken` variable blank: it is reserved for manual diagnostics, not used in requests. Never copy a production refresh token into a shared workspace. Admin login replaces the shared cookie, so run buyer refresh tests before staff login or sign back in as buyer first.
6. Folders 07–09 are optional/manual. Stripe and uploads require your connected accounts. Reset success requires a real token from YOUR email provider; the server stub does not email or expose it in production. Inspect `checkoutUrl`, complete Stripe test checkout in your browser, and wait for the signed webhook before running fulfillment. Do not manually mark payment paid.
7. For reload stress, log in as buyer, then run only the refresh request 80 times with the same cookie jar. All should return 200 and rotate the cookie. Rate-limit attack checks intentionally consume quotas; run those separately and wait for the 15-minute window before normal sign-in tests.
8. Postman does not enforce browser CORS/cookie blocking. In Chrome/Edge also test register/login, wrong/duplicate/weak/empty inputs, `/login?returnTo=/cart`, reload, two tabs, forgot/reset after email setup, and logout. In DevTools verify the refresh cookie is HttpOnly and production Secure; access tokens must not appear in localStorage.
9. Share redacted test results (request name, status and message), never passwords/tokens/connection strings.

The 63-request collection includes 49 core requests (folders 01–06) plus 14 optional provider requests. The core passed all 53 assertions against the SQLite harness. It has **not been run against your Atlas**. Run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-postman.ps1` from the project root for a guided laptop run; see `WINDOWS_SETUP.md` for expected output. This creates reviewable test records in your database. The core ends with logout, so sign in as buyer again before optional folders 07–09. Staff enquiry statuses and new-count fields are implemented; all staff actions require the backend admin role.
